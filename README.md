## 🚀 产品案例

### 案例一：Text2SQL 智能问数平台

> 让业务人员用自然语言直接查数据，降低数据消费门槛，释放数据资产价值

🔗 **技术仓库**：[text2sql-posttrain](https://github.com/wangfeng503/text2sql-posttrain)

#### 1. 产品背景与定位

**痛点**：企业数据散落在数十张业务表中，业务人员取数依赖数据团队排期，平均响应周期 2~3 天，运营分析效率低、决策滞后。数据团队 60% 人力消耗在重复性取数需求上，高价值分析工作被挤压。

**产品定位**：面向企业内部的 **"自然语言 → SQL → 数据结果"** 智能问数平台。业务人员用日常语言提问，系统自动生成可执行的 SQL 并返回结果，将取数周期从"天"缩短到"秒"。

**目标用户**：销售运营、风控分析、财务、渠道管理等非技术业务岗。

#### 2. 核心挑战

| 挑战 | 说明 |
|------|------|
| 语法准确性 | SQL 语法错误、表/字段映射错误会直接导致查询失败 |
| 业务逻辑对齐 | 同样的表述在不同业务线口径不同（如"实收金额"的计算规则） |
| 数据安全 | 敏感数据泄露风险、SQL 注入风险、全表扫描拖垮库 |
| 成本可控 | 大模型推理成本高，需在效果与成本间找到平衡点 |

#### 3. 产品方案设计

**三层目标解耦的产品架构**：

```
┌─────────────────────────────────────────────────────────┐
│                    用户接入层                             │
│  Web 对话界面 · 企业 IM 插件 · BI 工具嵌入 · API 调用     │
├─────────────────────────────────────────────────────────┤
│                    业务理解层（DPO 对齐）                 │
│  业务词表 · 口径规则库 · 行业知识 · 偏好对齐              │
├─────────────────────────────────────────────────────────┤
│                    Schema 映射层（RLVR 强化）             │
│  表结构理解 · 关联推理 · 字段映射 · SQL 执行反馈          │
├─────────────────────────────────────────────────────────┤
│                    语法规范层（SFT 基座）                 │
│  SQL 语法 · 基础查询能力 · 通用范式                       │
├─────────────────────────────────────────────────────────┤
│                    安全网关 & 审计                         │
│  只读权限 · 行数限制 · 脱敏规则 · 审计日志                │
└─────────────────────────────────────────────────────────┘
```

**关键产品决策**：

- **采用"小模型 + 后训练"而非调用大模型 API**：单条查询成本降低 80%+，数据不出内网，满足企业合规要求
- **三阶段训练策略产品化**：SFT 打底 → RLVR 提准确率 → DPO 对齐业务逻辑，对应产品从"能用"到"好用"的演进路径
- **SQL 安全网关作为必选模块**：所有查询必须经过语法检查、权限校验、LIMIT 强制、脱敏处理后才下发执行
- **可配置的业务规则引擎**：业务口径变更无需重新训练模型，通过规则库热更新即可生效

#### 4. 核心功能

| 功能模块 | 功能描述 | 用户价值 |
|---------|---------|---------|
| 自然语言查询 | 支持中文口语化提问，自动识别查询意图 | 零 SQL 基础即可取数 |
| SQL 解释 & 调优 | 展示生成的 SQL 并给出业务口径说明，支持人工修正 | 提升信任度，可学习 |
| 收藏 & 常用查询 | 高频查询一键复用，支持团队共享 | 降低重复提问成本 |
| 数据看板生成 | 多轮对话后自动生成可视化看板 | 从取数到分析一站完成 |
| 查询审计 | 所有查询留痕，支持敏感操作审批 | 满足企业数据合规 |
| 准确率评测 | 内置 EX 执行匹配 / 结构匹配 / 业务规则符合率三维评测 | 效果可量化、可验收 |

#### 5. 效果与指标

| 指标 | 基线（零样本） | SFT 后 | RLVR 后 | DPO 后 |
|------|--------------|--------|---------|--------|
| SQL 执行准确率 (EX) | ~45% | ~72% | **~86%** | **~89%** |
| 业务规则符合率 | ~30% | ~55% | ~70% | **~85%** |
| 单条推理成本 | - | - | 基础 14B INT4 量化 + vLLM 批处理，约 0.003 元/次 | |
| 取数响应时长 | 2~3 天（人工排期） | — | — | **秒级** |

> 💡 **产品洞察**：业务规则符合率比 SQL 语法准确率更能影响用户留存——SQL 写错了用户能看到报错，业务口径错了用户可能用了错误数据做决策而不自知，信任一旦崩塌就很难挽回。

#### 6. 我的角色与产出

- **产品规划**：从 0 到 1 定义产品形态，输出 PRD 与产品路线图，确定三阶段迭代目标
- **数据体系设计**：设计 Schema 注册表、业务词表、规则库三层数据资产，推动业务方共建
- **评估体系搭建**：建立"语法准确 → Schema 映射正确 → 业务逻辑符合"三级验收标准
- **成本优化**：推动 14B 小模型选型 + INT4 量化 + vLLM 推理优化，将推理成本控制在可商业化区间
- **上线策略**：设计"沙箱验证 → 小范围灰度 → 全量上线"的分阶段上线路径，控制风险

### 案例二：道路病害材料智能预测系统（道路 RAG）

> 基于历史案例库的智能匹配，让道路养护材料用量预测从"经验拍脑袋"到"数据说了算"

🔗 **技术仓库**：[材料清单模式识别](https://github.com/wangfeng503/material-list-pattern-recognition)

#### 1. 产品背景与定位

**痛点**：道路养护工程中，病害维修材料用量预测高度依赖工程师个人经验，不同人给出的预算差异可达 30%~50%。材料估多了造成库存浪费，估少了影响工期，项目成本管控难度大。行业内缺乏标准化的用量测算工具。

**产品定位**：面向道路养护施工单位的 **材料用量智能预测 SaaS**。输入病害类型、尺寸等参数，系统基于历史案例库智能匹配，输出材料清单与精准用量预测，辅助工程预算与材料采购决策。

**目标用户**：道路养护工程师、工程造价员、项目管理人员。

#### 2. 核心挑战

| 挑战 | 说明 |
|------|------|
| 非线性关系 | 材料用量与病害尺寸并非简单线性关系，不同材料规律不同 |
| 案例数据稀疏 | 每种病害的历史案例数量有限，难以支撑传统统计模型 |
| 多因素耦合 | 病害类型、尺寸、施工工艺、环境因素共同影响材料用量 |
| 工程信任门槛 | 工程领域对 AI 预测的接受度低，需要可解释性支撑 |

#### 3. 产品方案设计

**"案例匹配 + 函数拟合"双引擎架构**：

```
┌─────────────────────────────────────────────┐
│              用户输入层                       │
│  病害类型 · 尺寸参数 · 施工工艺 · 环境条件    │
├─────────────────────────────────────────────┤
│              智能匹配引擎（RAG 思路）         │
│  ┌───────────┐    ┌──────────────────────┐ │
│  │ 案例检索   │ →  │ 多维度相似度评分      │ │
│  │（向量+规则）│    │ 频率/面积/材料组合    │ │
│  └───────────┘    └──────────────────────┘ │
├─────────────────────────────────────────────┤
│              函数拟合引擎                     │
│  线性 · 平方根 · 立方根 · 二次方 · 三次方    │
│  自动验证最优变换 → 生成配置 → 预测计算       │
├─────────────────────────────────────────────┤
│              结果输出层                       │
│  材料清单 · 用量预测 · 置信区间 · 相似案例    │
└─────────────────────────────────────────────┘
```

**关键产品决策**：

- **采用"RAG 式案例匹配"而非端到端模型**：工程场景数据量小，黑盒模型难以获得信任；基于历史案例的匹配+可解释的相似度评分，更容易获得工程师认可
- **"外挂配置"而非硬编码**：病害单位、材料单位、变换类型全部写入配置文件，业务人员可自行调整，无需改代码发版
- **线性性验证前置**：每种材料自动验证与尺寸的最优函数关系，不强制假设线性，提高预测精度
- **API 化产品形态**：提供 RESTful API，方便集成到造价软件、项目管理系统等现有工具链中

#### 4. 核心功能

| 功能模块 | 功能描述 | 用户价值 |
|---------|---------|---------|
| 材料用量预测 | 输入病害类型和尺寸，一键输出材料清单和用量 | 分钟级完成过去数小时的测算工作 |
| 多变换拟合 | 自动验证每种材料的最优数学变换（线性/平方根/二次方等） | 预测精度远高于经验估算 |
| 相似案例推荐 | 展示最相似的历史案例及实际用量，提供参考依据 | 增强结果可信度，辅助决策 |
| 配置化管理 | 病害/材料/变换类型统一配置，无需代码修改 | 业务人员可自行维护规则 |
| RESTful API | 标准化 HTTP 接口，支持系统集成 | 可嵌入现有造价/项目管理系统 |
| Swagger 在线调试 | 交互式 API 文档，支持在线调试 | 降低对接成本，提高开发效率 |
| API Key 认证 | 接口安全认证，防止未授权调用 | 满足企业级安全要求 |
| 全链路日志 | request_id 追踪、耗时统计、IP 记录 | 问题排查 & 运营分析 |

#### 5. 效果与指标

| 指标 | 经验估算 | 本系统 | 提升 |
|------|---------|--------|------|
| 材料用量预测误差 | ±30%~50% | **±10% 以内** | 精度提升 2~4 倍 |
| 单次测算耗时 | 30 分钟~2 小时 | **< 3 秒** | 效率提升 99%+ |
| 覆盖病害类型 | 依赖个人经验 | **13 种常见病害** | 标准化覆盖 |
| 结果可解释性 | 无（纯经验） | **相似案例 + 匹配评分** | 决策可追溯 |

> 💡 **产品洞察**：在传统工程领域做 AI 产品，"可解释性"比"绝对准确率"更重要——工程师敢不敢用你的结果，取决于他能不能理解为什么是这个数。展示相似历史案例的做法，本质上是用"同行经验"为 AI 结果背书。

#### 6. 我的角色与产出

- **需求洞察**：深入养护施工一线调研，提炼出"材料用量预测不准"这一核心痛点
- **产品设计**：设计"案例匹配 + 函数拟合"双引擎产品方案，平衡精度与可解释性
- **算法选型**：与算法团队共同确定"模式识别 + 多变换拟合"技术路线，而非盲目上大模型
- **配置化体系**：推动业务规则配置化，降低产品迭代成本，赋能业务自助调整
- **API 产品化**：设计标准化 API 接口与认证体系，支持多种集成场景
- **落地验证**：与养护团队合作验证，预测误差从 30%+ 降至 10% 以内

## 🧠 产品方法论

### 我的产品观

1. **价值优先，技术其次**：先确认问题值不值得解决，再讨论用什么技术解决。AI 是手段，不是目的。
2. **用户信任是 AI 产品的生命线**：大模型产品的留存，本质上是信任问题。准确率、可解释性、纠错机制，都是在构建信任。
3. **小步快跑，可验证的迭代**：每个版本都要有可量化的验收指标，不靠感觉判断好坏。
4. **边界感比功能多更重要**：明确告诉用户"什么我做不好"，比吹得天花乱坠然后翻车强一百倍。

### 我擅长的产品类型

- 🏢 **B 端智能应用**：深入理解业务流程，将 AI 能力嵌入真实工作流
- 🤖 **大模型产品化**：从 POC 到规模化落地，踩过从"能用"到"好用"的坑
- 📊 **数据驱动的产品迭代**：搭指标、做实验、归因分析、持续优化
